## Context

自研云（vendor: tcloud-ziyan）主机申领推荐由 woa-server 离线任务 `apply_recommend_offline` 驱动。主流程在 `cmd/woa-server/logics/applyrecommend/logics.go` 的 `GenerateRecommend`：拉取已交付设备 → 补全地域 → 过滤无效镜像 / 不支持项目类型 → 聚合 → 写用户/业务推荐表 → 清理过期。聚合前跳过逻辑在 `skipDeviceForCount`。

申请单路径 `cmd/woa-server/service/task/scheduler.go` 的 `validateDeviceTypeForGreenAndRoll` 已按 Q1=B 校验机型组合：绿通/滚服禁止特殊型；绿通在 `CvmApplyConfig.Enabled` 时还要「机型族 ∈ 白名单且核数 ≤ 上限」。CVM 生产提单 `cvm.go` 有同名内联校验，**本期不改**。政策来自 `greenchannel.GetConfigs` 的 `CvmApplyConfig`。静态推荐读推荐表，预测推荐不读表。

本期把申请单里的机型组合判定抽成一个函数，离线写入前调用。只改离线写入（Q3=B），不改预测推荐（Q7=A），不改在线读路径，不改 CVM 提单。不把额度、预测余量、实时容量抽进公共函数。机型主数据与绿通配置在每一轮离线任务 / 每次申请单请求中各至多远程读取一次。函数长度不超过 80 行。

## Goals / Non-Goals

**Goals:**

- 申请单与离线写入共用同一个判定方法（F-004）；调用方只传需求类型和机型主数据，配置读取在方法内部完成。
- 在 `collectCounts` 计数前用该函数过滤不可用历史记录（F-001 / Q1=B）；空分组不占位（F-002）；逐条 Warn 含原因（F-003）。
- 离线每轮按页批量查机型、绿通配置按需至多读一次；I/O 失败则本轮任务失败（Q6）。
- 申请单对外错误文案保持现网不变。

**Non-Goals:**

- 改 CVM 生产提单（`CvmCreateReq` / `cvm.go`）。
- 在静态推荐 / 预测推荐 / Top-N 的在线返回路径上增加过滤（Q3=B）。
- 改预测推荐（Q7=A）。
- 改申领页 Top-N 接口契约。
- 把完整提单前校验链搬进离线任务。
- 改 Top-K / 去重键 / 先人后业务 / 预测内外回退。
- 机型替换或降级兜底；清理源表；改对外请求响应字段。
- 覆盖其他云厂商。

## Decisions

### 决策 1：过滤加在 `collectCounts` 计数之前

**选择**：地域补全与有效镜像查询之后、计数之前：先为本轮机型按页批量查主数据，再按需求类型分别调用判定函数；循环内先 `skipDeviceForCount`，再按判定结果跳过不允许的记录。

**理由**：不可用组合不进聚合 map；空分组走既有过期清理，满足 F-002；不改读路径，满足 Q3=B。

**备选（否决）**：

- 在线读路径过滤：Q3=B 已否。
- 写入推荐表前再滤：聚合结果已按组合分组，空分组处理更绕。
- SQL 写死白名单机型：政策是运营可配的，会与 `CvmApplyConfig` 漂移。

### 决策 2：上层只调一个判定函数

**选择**：把申请单内层判定抽到已有的主机申领 logics `cmd/woa-server/logics/task/scheduler`，只导出一个函数：

```
CheckDeviceType(kt, requireType, infos) (map[string]string, error)
```

挂在已有主机申领 `scheduler` 上。入参用现有需求类型和机型主数据，返回不允许的机型到原因；非绿通/滚服直接通过。内部用已注入的绿通 logics 按需读一次配置。调用方不传 `gcLogics`、不直接 `GetConfigs`。离线任务注入已有的 `scheduler.Interface`。规则：

- 特殊型：不允许，原因「不支持特殊机型」。
- 非绿通、或绿通开关关闭：非特殊型允许。
- 绿通且开关打开：机型族不在白名单 →「机型族 {family} 不在允许范围」；核数超限 →「CPU核数 {n} 超过上限 {limit}」。
- `Reason` 仅供离线 Warn；申请单错误文案仍由调用方写死现网字符串。

| 调用方 | 调用方自己做 | 调用判定函数 |
|---|---|---|
| 申请单 `scheduler.go` | 非绿通/滚服直接 return；从子单收集机型并按原路径查主数据；现网错误文案 | 一次 `CheckDeviceType` |
| 离线 `applyrecommend` | 本轮一次查出机型主数据，按需求类型带上该类型实际出现的机型调用 `CheckDeviceType` | 计数循环里按结果跳过并 Warn |
| CVM `cvm.go` | **不改**，继续用原内联校验 | 不调用 |

申请单维持原行为：只校验查询命中的机型，主数据未命中的请求机型不进入判定。离线对主数据未命中的机型按「机型数据不存在」跳过，不写入推荐表（不限绿通/滚服）。`CheckDeviceType` 对非绿通/滚服直接返回空拒绝表，不读绿通配置。

**性能：** 每次申请单请求、每一轮离线任务：机型主数据按页批量查询，绿通配置按需至多一次远程。离线循环内不打远程。

**备选（否决）**：Checker / 窄接口编排；把读配置和判定拆成多个导出函数。申请单与离线的 I/O 和错误出口不同，再抽一层编排过重；多个导出函数会让调用方自己拼配置读取。

### 决策 3：判定函数放在主机申领 scheduler 包

| 符号 | 职责 |
|---|---|
| `scheduler.CheckDeviceType` | 按需求类型校验机型；内部按需读绿通配置；调用方不传 gcLogics |

申请单继续走原有的 `configLogics.Device().ListDistinctDeviceType`，不改查询入口。离线在 `applyrecommend` 内自己批量查机型。不把额度、预测余量、实时容量抽进该函数。不放到 green-channel：该包只负责绿通配置与统计，机型组合判定属于主机申领。

### 决策 4：离线日志逐条 Warn，原因来自函数返回值

**选择**：离线侧使用函数返回的中文 `reason`。不打汇总报表。

### 决策 5：单测覆盖判定规则；调用方测收集与 skip

**选择**：

- 判定表驱动：绿通 + ITA5 不允许；绿通 + 标准型且核数 ≤ 上限允许；绿通/滚服 + 特殊型不允许；滚服 + 非特殊型允许；政策开关关闭时绿通非特殊型不因族/核数被拒；常规项目调用 `CheckDeviceType` 直接通过（空拒绝表）。
- 导出函数：滚服路径在无绿通配置依赖时一次调用即可得到拒绝列表。
- `TestSkipDeviceForCount_RequireType` 继续通过。
- 申请单现网错误文案不写进判定函数。

## Risks / Trade-offs

- **[风险] 过滤后静态推荐变少或整组被过期清理删空** → 预期。空列表仍成功（Q4）。
- **[风险] 预测推荐仍可能打出 ITA5 + 绿通** → Q7=A 已接受。
- **[风险] 上线后到下一轮 cron 前仍可能打出旧组合** → Q3=B 已接受。
- **[风险] CVM 提单与抽出函数不是同一份代码** → 本期明确不改 CVM；CVM 与申请单现网规则本来就各自维护。
- **[风险] 申请单对主数据未命中的请求机型仍放过** → 维持申请单原行为；离线对未命中机型跳过。
- **[风险] `GetConfigs` 或机型查询失败** → 本次请求 / 本轮任务失败，不放行未校验数据（Q6）。

## Migration Plan

1. 部署含该判定函数的 woa-server（无 DDL、无接口字段变更、无新增 IAM）。
2. 等待下一轮 `apply_recommend_offline`（默认间隔 720 分钟）成功跑完，或手动 `POST /api/v1/woa/apply_recommend/sync`。
3. 回滚：回退本次变更并重新部署；无需反向 DDL。
4. 性能：测试环境同一份已交付记录，修复前后各 3 轮，任务耗时增幅 < 5%；离线循环内无按条远程调用。
