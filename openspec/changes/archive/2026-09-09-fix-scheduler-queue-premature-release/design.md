## Context

woa-server 的自研云主机申领调度子系统由三段构成：informer（list & 5s 轮询，把变更的子单/生产记录入队）→ dispatcher / matcher（多 worker 从队列取元素并处理）→ generator（向云梯 CRP 下单生产）。两个 informer 各自持有一条 `k8s.io/client-go/util/workqueue` 的 `RateLimitingInterface` 队列：

- apply informer（`cmd/woa-server/logics/task/informer/apply/apply.go`）派发申请子单 `suborder_id`，消费方是 dispatcher 的 20 个 worker（`dispatcher.go:52`）
- generate informer（`cmd/woa-server/logics/task/informer/generate/generate.go`）派发生产记录 `generate_id`，消费方是 matcher 的 60 个 worker（`matcher.go:95`）

**workqueue 的契约**是三段式的：`Get()` 取出元素并将其标记为「处理中」；元素处于处理中期间，同一元素的重复 `Add()` 只被合并暂存（dirty set），不会再次派发给别的 worker；直到 `Done()` 被调用，元素才离开处理中集合，暂存的入队通知才转为一次新的派发。这层「同一元素同一时刻至多一个 worker」的互斥，是整条调度链路唯一的并发保护——链路上没有分布式锁、没有数据库行锁、没有乐观版本号。

**当前的失效点**在于 `Get()` 与 `Done()` 之间的窗口被压缩为零：两个 informer 的 `Pop()` 在把 id 返回给调用方之前就完成了释放，元素实际上从未处于处理中状态。而 informer 每 5s 轮询一次并把状态仍在流转中的子单/生产记录重新入队（`apply.go:133-233` 的 `pollLoop` / `pollApplySubOrders`），一轮处理未结束时同一元素被再次入队是高频事件，于是这些入队立即转为新的派发。

失效的后果由下游放大：`generator.go:138-154` 的 `GenerateCVM` 是生产入口总闸，它先调 `getScheduledDeviceStats`（`generator.go:331-347`）读「已落库设备数 + 在途生产数」，再判断 `scheduledCount >= order.TotalNum`。这是典型的 check-then-act：总闸的算法本身没有漏算在途数，但它的正确性依赖「同一子单串行处理」这一前提。当两个 worker 并发进入时，两者在任何一方写入新生产记录之前读到同一份快照，双双通过总闸，各自按 `total_num − scheduledCount` 计算 `replicas` 下单——同一批缺口被下单两次。matcher 侧同源：两个 worker 并发读到相同的 `IsMatched = false`（`matcher.go:160-164`）与相同的设备列表，对同一批设备重复执行初始化、压测与交付。

**约束**：不引入新的并发原语（分布式锁 / DB 锁 / 版本号）、不改表结构、不改对外接口、不改交付数统计口径；woa-server 的调度只在 master 节点运行（`runWorker` 开头对 `informer == nil` 的判断即此语义），因此进程内互斥足以覆盖。

## Goals / Non-Goals

**Goals:**

- 让队列元素在**整个本轮处理期间**真正处于 workqueue 的「处理中」状态，恢复「同一子单 / 同一条生产记录同一时刻至多一个 worker」的互斥前提，使 `GenerateCVM` 的 check-then-act 总闸重新成立
- 把释放时机交给**掌握处理边界的一方**（dispatcher / matcher 的 `runWorker`），并保证在该函数的所有退出路径（正常返回、提前返回、错误返回、panic 展开）上都发生且只发生一次
- 保住活性：处理结束后元素必须能被下一轮轮询再次派发，不得出现「收口成功但再也调度不到」的退化
- 覆盖走同一 informer 的全部资源类型，不针对 CVM 做特化

**Non-Goals:**

- 不做超发告警、存量单据超发对账、前端「已交付 > 总数」提示、超发机器自动回收
- 不处置单据 104398 已超发的 22 台机器
- 不改动 `generator.go` 的入口总闸算法与在途数统计逻辑（它的失效原因是前提被破坏而非算法有误）
- 不改 `total_num` / `success_num` / `pending_num` 的语义与前端展示口径
- 不引入自动化单元测试作为本次的验收手段
- 不解决云梯侧单批多产（若存在）这一潜在的第二超发来源

## Decisions

### 决策 1：把释放动作从 informer 内部搬到调用方，`Pop` 只负责取出

`Pop()` 只做「取出 + 类型断言」，不再对成功返回的元素调 `Done()`；informer 的 `Interface` 暴露一个与 `Pop` 配对的 `Done(id string)`（`apply.go:39-47`、`generate.go:44-50`），由调用方在本轮处理结束时调用。

**为什么**：workqueue 的「处理中」窗口天然应该等于「调用方处理这个元素的时间」。informer 不知道调用方什么时候算处理完，任何由 informer 自行决定的释放时机都只能是猜测；把释放权交给调用方是唯一能让窗口与处理边界对齐的做法。

**考虑过的替代方案**：

- *让 `Pop` 返回一个 `done func()` 闭包*：能强制配对感更强，但改变了 `Interface` 的返回签名，两个调用点与所有 mock 都要跟着改，且闭包捕获会掩盖「释放的是哪个 id」这一在日志排障时有用的信息。收益不抵成本。
- *informer 内部起一个「处理超时自动释放」的看门狗*：能兜住调用方漏调 `Done` 的情况，但超时值无从设定——一轮分 Campus 生产的耗时随可用区数量与云梯响应波动，设短了会重新引入重复派发，设长了兜不住。引入了一个需要调参的新故障源。
- *在 `getScheduledDeviceStats` 之后加数据库层的乐观锁或唯一约束*：能防住跨进程并发，但本场景是进程内并发，且会引入表结构变更与写冲突重试逻辑，违背「不改表结构、不引入新并发原语」的约束。互斥语义本来就该由队列提供。

### 决策 2：调用方用 `defer` 在取出成功后立即登记释放

dispatcher 与 matcher 的 `runWorker` 在确认取到有效 id 之后、进入业务处理之前，立即 `defer informer.Done(id)`（`dispatcher.go:103`、`matcher.go:140`）。

**为什么**：`runWorker` 有多条退出路径——`dispatchHandler` 返回错误、matcher 的生产记录状态未就绪提前返回（`matcher.go:152-157`）、`IsMatched == true` 提前返回（`matcher.go:159-164`）、以及下游 panic 被 `wait.Until` 捕获后的栈展开。`defer` 是 Go 里唯一能一次性覆盖全部退出路径的配对手段；逐条退出路径手写 `Done()` 必然会在后续迭代中被漏掉，而漏掉一次的代价是该元素永久卡死（见风险 1）。

**`defer` 的登记位置必须在两个判空之后**：`Pop()` 在队列 shutdown 时返回 `("", nil)`、在类型断言失败时返回 `("", err)`，这两种情况下**没有**需要调用方释放的元素——shutdown 路径本就没取到东西，断言失败路径已由 `Pop()` 内部对那个非预期对象调过 `Done()`（`apply.go:118-123`、`generate.go:122-127`）。若把 `defer` 提到判空之前，会对空串调 `Done()`，等于凭空释放一个从未被取出的键。

### 决策 3：异常元素在 `Pop()` 内部就地释放，不外泄给调用方

类型断言失败时，`Pop()` 直接对那个非预期对象调 `Done()` 并返回 error。

**为什么**：调用方拿到的是 `string`，它无法引用那个非 string 的原始对象，因而无法释放它。只有 `Pop()` 手里有 `obj`。不释放的话，该对象会永久留在 workqueue 的处理中集合里占位。这条路径与决策 2 的配对规则不冲突：责任归属清晰——「谁最后持有元素引用，谁负责释放」。

### 决策 4：`Forget(obj)` 合并为 `Get()` 之后一次性调用

改动前 `Forget(obj)` 位于类型断言之后，成功分支与断言失败分支各调用一次；改动后合并为 `Get()` 之后立即调用一次（`apply.go:116`、`generate.go:120`）。非 shutdown 的每条路径上 `Forget` 仍恰好对同一个 obj 调用一次，语义等价。

**为什么**：`Forget` 清的是 RateLimiter 的失败退避计数，与 `Get()` / `Done()` 维护的「处理中」集合是两套彼此独立的机制，它的位置不影响本次要恢复的互斥语义，重试退避行为也不变。合并后两个分支不再各写一遍，后续迭代中新增退出路径时不会漏掉其中一处。

## Risks / Trade-offs

- **活性退化（本次最大的反向风险）**：处理中窗口从「近乎为零」变成「一整轮处理」。若任何一条退出路径漏掉释放，该元素在 informer 重建（即进程重启）前将永不被派发；对一张 `wait_for_match` 的子单而言，这意味着它停止交付且无人察觉，危害高于原有的重复派发缺陷 → **缓解**：用 `defer` 而非逐路径手写（决策 2）；在 `Pop` 的注释里写明配对契约与两个方向的后果（`apply.go:106-109`、`generate.go:110-113`），使后续修改者在改动 `runWorker` 时能看到约束；验收上以 AC-P01「20 条注入子单被派发次数 ≥2 的比例为 100%」正面证明活性未退化，而不是只证明「没有重复派发」。

- **对空串或未取出元素误调 `Done`**：workqueue 对未处于处理中集合的键调 `Done()` 是静默无操作，不会 panic，但会让「处理中」集合的记账与实际不符，掩盖真实问题 → **缓解**：`defer` 严格登记在两个判空分支之后（决策 2）。

- **吞吐下降**：同一子单被串行化后，单位时间内该子单的调度轮次减少。→ **评估为可接受**：worker 池是 20 / 60，串行化只发生在**同一元素**上，不同子单之间仍完全并行；而重复派发本来就不产生有效吞吐，只产生超发。本需求不引入新的性能指标要求。

- **长时间处理阻塞后续轮次**：一轮分 Campus 生产若耗时很长，该子单在此期间收不到新的派发。→ **评估为可接受且符合预期**：这正是要的语义；本轮结束后轮询会在 5s 内重新入队。

- **残余风险：可能存在第二超发来源**。需求文档「假设 4」明确标注「单据 104398 超发 22 台的成因即本缺陷」这一判断未经该单生产日志逐条回放验证。若云梯侧存在单批多产，本次上线后 AC-005 / AC-P03 仍可能不达标 → **缓解**：AC-P03 设置 30 天观察窗口，用于暴露而非掩盖第二来源；若观察期内仍有新增超发，另立需求处理，不回退本次改动（本次改动的正确性不依赖该假设成立）。

## Migration Plan

- **部署**：随 woa-server 常规发布滚动上线。调度逻辑只在 master 节点生效，无多副本一致性问题；无数据迁移、无表结构变更、无配置项变更、无前端联动。
- **生效时点**：新进程启动后 informer 重建，行为即刻生效。存量队列不跨进程保留，无需清理。
- **回滚**：回退到上一版本二进制即可，无残留状态需要清理。回滚后行为回到「重复派发 + 可能超发」，不会造成数据不可恢复的损坏（超发出的机器仍是真实机器，走运营流程处置）。
- **上线后观察**：按 AC-P01 / AC-P02 观察调度日志的派发次数与处理窗口相交情况（重点确认活性未退化），按 AC-P03 每日 SQL 统计新增超发子单数，连续 30 天。
