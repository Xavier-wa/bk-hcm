# Design — 指令模板模式 · 主机申领表单

> 关联 PRD：`.hcmfe/workflow/iter-chatbot-custom-msg-command-template/prd.md`
> 设计稿来源：用户分多次提供 PNG（对话附件，不入库）。无 Figma 链接。
> 机制：agent 下发 `CUSTOM` event（靠 `name`/`template_id` 区分）→ 前端按 id 命中**内置模板库**组件渲染。本文档识别稿面对应的模板形态、布局、交互、状态。
> 惯例：所有模板均需**全页 + 浮窗**两形态响应式（沿用 jsonschema 迭代的 `container-type`/`@container` 方案）。
> 关键决策已确认（见 §9），本迭代 A/B/C 三个模板均做。

## 1. 稿面与模板清单

> 用户分多轮供图、图号会复用，这里统一按内容命名。

| 稿面内容 | 模板（暂名，最终 id 由 api 阶段对齐） | 本迭代 |
|---|---|---|
| 全页整体布局（参考卡片在对话流中的方位） | —（上下文参考） | 参考 |
| 申领方案推荐（键值表 + 翻页 + 三按钮，可交互） | `host_apply.recommend` | ✅ 做 |
| 预提单数据（稿面「方案已解析」：多条配置表格 + 行内编辑 + 全屏） | `host_apply.preorder` | ✅ 做 |
| 调整配置弹窗（**仅左侧表单**，由预提单表格行内编辑触发） | `host_apply.adjust` | ✅ 做 |

> **流程本质（重要）**：A、B 都是 **agent 下发的 CUSTOM 模板**，不是前端状态切换。用户在 A「选择/提交申领方案」→ 回传 agent → **agent 再返回预提单数据** → 前端渲染为 B。稿面里 B 的标题是「方案已解析」，但其数据来源是 **agent 提交申领方案后返回的预提单数据**，并非前端对 A 方案的本地解析。
| 申领方案/已解析的**只读展开态**（完成后默认收起、可展开、展开只读） | 各模板的只读态 | ✅ 做 |

> 卡片头部「已调用 X 个工具」「思考了 X 秒」**不属于本模板**——由 chat-x 默认 message 渲染，模板只渲染其下的业务卡片内容。

## 2. 对话流中的方位

承接 jsonschema 迭代：吸顶「云账号」回显条 → 用户消息（如「主机申领」）→ 已选账号摘要卡 → **本迭代的指令模板卡片**依次出现在 AI 消息气泡区。模板卡片宽度与既有 AI 消息卡片一致（全页主内容区宽、浮窗整宽）。

## 3. 模板 A：申领方案推荐（本迭代）

agent 在用户选定账号后返回推荐方案，可能有多条，分页浏览。

### 布局
- **头部提示语**：普通文本（云图标 + 「根据您选择的账号，建议的申领方案如下，请确认是否符合您的业务需求」）。按 jsonschema 迭代约定，提示语为自然消息文本，模板卡片本体从分页标题开始。
- **分页标题行**：左「申领方案推荐 1/3」，右翻页按钮（多条方案时 `上一个`/`下一个`；首/尾条对应按钮置灰；单条时无翻页）。
- **提示横幅**（可选，数据驱动）：浅黄底 + 警示图标，如「SA3.4XLARGE32 库存充足，可替代您提单的机型 SA5.4XLARGE32」。无该提示时不渲染。
- **参数明细**：键值两列表格（label 右对齐灰字 / value 左对齐），字段顺序按稿面：需求类型、地域、可用区、机型、操作系统、资源分配方式、申请数量、计费模式、系统盘、数据盘。字段由数据驱动，缺失项不渲染；value 支持多行/富文本（如计费模式「预测内 12 台-包年包月；预测外 8 台-按量计费」）。
- **操作按钮**（底部，左对齐）：`选择方案`（主按钮）、`添加到配置清单`、`调整配置`。

### 交互
- **选择方案**（= 提交申领方案）→ 向 agent 回传（见 §6 提交语义）；**agent 随后返回预提单数据**，前端渲染为模板 B（B 是 agent 下发的下一条 CUSTOM 模板，非前端直接切换）。
- **添加到配置清单** → 跳转到**主机申请页面**（本迭代只做跳转 + 预留入口，回填后续需求再做，见 §7）。
- **调整配置** → 打开模板 C「调整配置」弹窗（仅左侧表单）。
- **翻页** → 在多条推荐方案间切换，分页标识 `当前/总数` 同步。

### 状态
- 选择态（默认，可操作）。
- 只读展开态：完成（已选择/已确认）后整卡转为**只读**，默认收起为摘要行、可点击展开预览，**展开后不允许任何交互**（所有按钮置灰），详见 §5.1。

## 4. 模板 B：预提单数据（稿面「方案已解析」，本迭代）

**数据来源**：用户在模板 A 提交申领方案后，**agent 返回的预提单数据**（多条申领配置），由 agent 以 CUSTOM 模板下发，前端渲染为可逐条确认/编辑的表格。**不是**前端对 A 方案的本地解析。

### 布局
- **头部提示语**：云图标 + 「方案已解析，请确认以下参数后提交」（稿面措辞）。
- **提示横幅**：浅黄底 + 警示图标，如「已解析 4 条申领配置，请逐条确认参数，可点击右侧编辑 icon 进行编辑；如需使用页面申领，可点击『添加到配置清单』」。
- **右上角**：`全屏`按钮（图标 + 文字），用于放大查看多列表格。
- **配置表格**：多列 + 多行，列按稿面：机型、操作系统、申请数量（可排序）、地域、可用区、计费模式、需求类型，行尾**编辑 icon**（逐条编辑）。
- **操作按钮**（底部，左对齐）：`确认方案`（主按钮）、`添加到配置清单`。

### 交互
- **行内编辑 icon** → 打开模板 C「调整配置」弹窗，编辑**该条 agent 返回的预提单数据**；保存后写回该行。
- **全屏** → 表格全屏/大窗查看（窄浮窗下尤为必要）。
- **确认方案** → 提交并向 agent 回传（见 §6 提交语义）。
- **添加到配置清单** → 跳转主机申请页面（本迭代只跳转 + 预留入口，见 §7）。

### 状态
- 待确认（可编辑）。
- 只读展开态：确认后整卡转只读、默认收起、可展开预览、展开不可交互（同 §5.1）。

### 响应式
- 全页：完整多列表格。
- 浮窗：列多宽窄，优先横向滚动或「每条配置折叠为卡片」展示；`全屏`按钮在浮窗下作为查看兜底。具体取舍 coding 阶段按容器宽度定，须保证关键列（机型/数量/地域）可读。

## 5. 模板 C：调整配置弹窗（本迭代）

> 由模板 B「方案已解析」表格**行内编辑 icon** 触发，编辑的是 **agent 返回的预提单数据**（单条配置）。形态为**弹窗**（标题「调整配置」，右上角关闭 X）。

- **仅左侧表单**（按用户确认：**不要**稿面右侧的「快捷切换机型」面板）：申请数量（数字步进，必填）、地域（必填）、机型（必填）、操作系统、资源分配方式、需求类型、计费模式（只读，「基于预测状态自动推导」）、系统盘（类型 + 容量，必填）、数据盘（类型 + 容量 + 数量）。
- **底部**：`保存修改`（主按钮）/ `取消`。
- **数据流**：弹窗以该行预提单数据回填初始值 → 用户修改 → `保存修改` 写回模板 B 对应行（修改后的完整配置参与后续 `确认方案` 回传，见 §6）。
- **表单实现**：倾向复用项目 `components/form` 能力与现网控件/校验体验（具体方案 coding 阶段定）。

### 5.1 只读展开态（模板 A / B 通用）

完成的步骤（已选择方案 / 已确认方案）统一遵循：
- **默认收起**为摘要行（绿色对勾 + 摘要文案 + 展开 chevron），与 jsonschema 迭代收起态一致。
- **点击展开**：展示该步骤的完整内容（方案预览键值表 / 已解析表格），标题切换为「申领方案预览 N/M」等只读措辞，翻页仅用于预览。
- **展开后不允许任何交互**：`确认方案`/`添加到配置清单`/`调整配置` 等全部置灰禁用，行内编辑不可用。
- **历史回放**：历史会话再次打开时还原为只读展开/收起态，内容与当时提交一致（沿用 jsonschema 历史回放约定）。

## 6. 提交语义（向 agent 回传）

整条链路有**两次**向 agent 回传（均沿用 jsonschema 的上行通道，具体字段 api 阶段定），每次回传后对应卡片转只读态（§5.1），agent 返回下一条模板：

1. **模板 A「选择方案」（提交申领方案）**：回传所选**方案 id** → agent 返回预提单数据（渲染模板 B）。
2. **模板 B「确认方案」（提交预提单）**：
   - **未编辑**：回传该预提单的标识/原始数据。
   - **编辑过**（经模板 C 调整某些行后）：回传**修改后的完整配置数据**。

> 原则：能用 id 表达就回传 id；用户改过配置则回传完整数据。

## 7. 跨页跳转说明（「添加到配置清单」，本迭代只做跳转）

- 本迭代**只做页面跳转**：点击后跳转到**主机申请页面**，并**预留好携带数据的入口**。
- **回填到配置清单的逻辑本迭代不做**，按规范放到后续「回填」需求里实现。
- 跳转须走 `routerAction`（项目规范），不直接用 vue-router 实例。
- 「联动打开 AI 助手」等进一步联动随回填需求一并做。

## 8. 与 PRD 的对应 / 差异

- PRD「首个模板=主机申领表单」在稿面上实际是**一组模板**（推荐 A → 已解析 B → 调整配置弹窗 C），本迭代 A/B/C 均做。已据稿面细化，不改 PRD 机制结论。
- PRD「表单 / 只读卡片 / 静态+动态选项」：模板 A/B 为「确认型卡片 + 表格」，模板 C（调整配置弹窗）是典型表单，承载「复用 components/form」能力；C 表单内的选项（地域/机型/操作系统等）静态/动态来源在 api 阶段对齐。

## 9. 关键决策（已确认）

- **QD1 模板 C（调整配置）→ 做**。但**不是**从推荐卡直接进一张大表单页，而是落在**模板 B 行内编辑**：点击「方案已解析」表格行尾编辑 icon，弹出「调整配置」弹窗，编辑该条 **agent 返回的预提单数据**；**仅保留左侧表单**，去掉稿面右侧「快捷切换机型」面板。
- **QD2 提交语义 → 向 agent 回传**：未编辑回传**方案 id**；编辑过则回传**修改后的完整表单数据**。
- **QD3「添加到配置清单」→ 本迭代只做页面跳转**：直接跳转到主机申请页面并预留携带数据的入口；回填配置清单、联动开助手等按规范放到后续「回填」需求实现。
- **QD4 只读/历史回放 → 做**：完成步骤默认收起、可展开、展开仅只读（按钮全置灰）、历史可还原（见 §5.1）。

## 10. 遗留到 api 阶段

- 各模板 `template_id`/`name` 命名与 `CUSTOM` event 数据结构（参数明细字段、解析配置列表字段、调整表单字段与校验、value 多行/富文本约定）。
- 提交回传的上行字段结构（方案 id / 完整配置数据）。
- 调整配置弹窗内动态选项（地域/可用区/机型/操作系统等）的来源（静态内联 or 接口）。
- 「添加到配置清单」跳转目标路由 + 预留入口的传参形态。
