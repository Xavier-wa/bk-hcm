# PRD — aiagent chatbot 自定义消息展示 · 指令模板模式

> 父需求：aiagent - chatbot自定义消息展示（`<TAPD_HOST>/tapd_fe/69995598/story/detail/1069995598134649873`）
> 本子需求：指令模板模式（`<TAPD_HOST>/tapd_fe/69995598/story/detail/1069995598134649996`）
> 兄弟迭代：jsonschema 模式（已 done，落地「云账号选择」简单选项渲染）
>
> 机制/场景关键点已与用户确认（见 §6），本迭代据此推进。TAPD 子单本身无描述，需求细节以本文档为准。

## 1. 背景与目标

父需求要在 chatbot 中基于 chat-x 组件做「自定义消息展示」，拆为两个子模式：

- **jsonschema 模式**（已完成）：承载**简单选项类**交互（泛化 HITL 选择），本质是单选/多选卡片，已用于「云账号选择」。
- **指令模板模式**（本迭代）：承载**复杂表单 / 只读卡片 / 任意自定义渲染**类交互——即 jsonschema 模式当初有意不做、留给本迭代的能力。

**机制（已确认）**：采用**前端内置模板库**方案——agent 下发「指令」（`template_id` + 数据），前端按 `template_id` 映射到内置模板组件进行渲染（而非由 agent 下发完整 UI schema 让前端通用引擎解析）。协议与 jsonschema 模式**统一**：同为 SSE 的 `CUSTOM` event，靠 `name` 区分模式 / 模板。

**目标**：让 agent 能在对话流中下发「指令模板」类自定义消息，前端按指令从模板库解析渲染为可交互**表单**、**只读卡片**或其它自定义展示；用户填写/操作后，将结果回传 agent，驱动后续流程。本迭代落地**首个真实模板「主机申领表单」**（承接 jsonschema 迭代「云账号选择」的下一步），同时把「按指令→模板库解析→渲染」沉淀为可复用机制。

## 2. 用户故事

- US1：作为用户，当 agent 需要我补充一组结构化信息（如一张表单）时，我能在对话里直接看到一张**可填写的表单卡片**，填完提交即可，无需跳转其它页面。
- US2：作为用户，当 agent 要向我展示一组结构化结果/详情时，我能在对话里看到一张**只读信息卡片**，清晰分组、可读性好。
- US3：作为用户，表单里的下拉/选择项，无论它的候选值是**固定配置**还是**实时从后端拉取**，都能正常加载与选择。
- US4：作为用户，表单的填写体验（控件样式、校验提示、必填标识等）与产品内其它表单**保持一致**，不突兀。
- US5：作为用户，提交后该消息进入**只读态**回显我的填写内容；历史会话再次打开时，能看到当时提交的内容（只读）。

## 3. 范围（本迭代）

用户已确认本迭代核心能力包含：

1. **模板库解析机制**（框架）：建立「agent 下发 `template_id` + 数据 → 前端按 id 从内置模板库匹配模板组件 → 渲染」的通用机制，可扩展新增模板。（核心框架）
2. **首个模板「主机申领表单」**（场景）：在模板库中实现主机申领表单模板，承接云账号选择之后的申领信息填写。（核心场景）
3. **表单类自定义渲染**：agent 下发表单数据 → 前端渲染可交互表单 → 用户填写后回传。
4. **只读卡片 / 任意展示类自定义渲染**：agent 下发只读结构 → 前端渲染信息展示卡片。
5. **选项数据来源**：表单中的可选项**同时支持静态（随消息内联）与动态（调用后端接口拉取）**两种来源。
6. **与产品现有表单体验一致**：填写体验、控件、校验与现网表单统一（技术上倾向复用现有表单能力，具体方案留 design/coding）。

### 提交与回显

- 提交后消息转为只读态，回显用户填写内容；与 jsonschema 模式一致地支持**全页 / 浮窗两种形态**与**历史回放只读**。

## 4. 不在本迭代范围

- 多步骤向导 / 跨消息表单联动（除非确认场景需要）。
- agent 侧模板的配置与下发逻辑（后端/agent 负责，前端只消费）。
- jsonschema 模式已覆盖的简单单选/多选选项卡片（属上一迭代）。

## 5. 验收标准（草稿，待场景确认后细化）

- AC1：agent 下发指令模板类消息后，对话流中渲染出对应的表单/卡片，结构与下发内容一致。
- AC2：表单必填项未填写时无法提交，并给出校验提示；全部合法后可提交。
- AC3：表单中动态来源的选择项能正确发起请求并展示候选；静态来源直接展示。
- AC4：提交后消息进入只读态并回显填写值；刷新/重进历史会话仍为只读且内容正确。
- AC5：全页与浮窗两种形态下渲染与交互均正常（沿用 jsonschema 模式的响应式约定）。

## 6. 关键决策（已确认）与遗留项

已确认（作为本迭代依据）：

- **Q1 指令模板形态** → **①预定义模板 id + 数据，前端内置模板库**。本迭代做「模板库 + 解析渲染机制」，不做通用 UI schema 渲染引擎。
- **Q2 与 jsonschema 模式的边界** → **协议统一**：同为 SSE `CUSTOM` event，靠 `name` 区分模式/模板（沿用 jsonschema 迭代的事件处理与渲染分发架构）。
- **Q3 本迭代落地场景** → **做「主机申领表单」**（接云账号选择的下一步），**同时**建立按指令→模板库解析的通用机制（框架 + 首个真实模板一起做）。
- **Q4 设计稿** → **有，design 阶段提供**（Figma/PNG 在 design 阶段识别）。

遗留到后续阶段：

- **Q5 字段/Schema 结构（→ api 阶段）**：主机申领表单的字段、控件类型、校验规则、动态选项接口约定、`template_id`/数据协议结构等，按真实 eventstream/接口核对（参照 jsonschema 迭代做法）。
