## 1. 前置基线（已完成，非本次新增）

主机申领 chatbot 的对话申领链路已在迭代 `iter-chatbot-custom-msg-command-template`（父需求 `req-aiagent-chatbot-custom-message`「chatbot 自定义消息展示 - 指令模板模式」）中实现，包含四类对话卡片：

- **卡片 A · 申领方案推荐**：agent 下发一个/多个推荐方案，用户选择其一。
- **卡片 B · 预提单 / 确认配置**：展示待确认的申领配置（可逐条编辑），用户确认。
- **卡片 C · 调整配置弹窗**：由 B 行内编辑触发的配置编辑弹窗，保存写回该行。
- **卡片 D · 确认提交申请单**：最终只读确认卡，用户点击提交。

上一迭代遗留（本迭代要解决的部分）：

- 卡片中各字段值**直接展示后端编码/ID**（如地域 `ap-nanjing`、机型 `S3.MEDIUM4`、镜像 `img-fjxtfi0n`、计费模式 `PREPAID` 等），可读性差。
- 卡片 C 调整配置弹窗的下拉选项**使用前端静态枚举**，与真实可申领资源不一致。

---

## 2. 本迭代目标

提升主机申领对话流的**信息可读性**与**配置准确性**：让用户在对话卡片里看到的是「人能看懂的名称」而非后端编码；在修改配置时，下拉候选项来自真实数据接口，避免选到不可用 / 不存在的资源。

---

## 3. 本迭代功能需求点

### F1 申领流程展示值：编码/ID → 名称

- F1.1 主机申领对话卡片中，原本展示为后端编码 / ID 的字段，统一展示为对应的**可读名称**。
- F1.2 覆盖卡片范围：**卡片 A（方案推荐）、卡片 B（预提单 / 确认配置）、卡片 D（确认提交申请单）** 的只读展示位，以及编辑后回显。
- F1.3 覆盖字段范围（全部 8 个编码字段）：
  - 地域 `region`
  - 可用区 `zone`
  - 机型 `device_type`
  - 镜像 `image_id`
  - 计费模式 `charge_type`
  - 需求类型 `require_type`
  - 资源分配方式 `res_assign`
  - 磁盘类型 `disk_type`（系统盘 / 数据盘）
- F1.4 名称缺失兜底：若某编码查不到对应名称，需有合理兜底（如回退展示原编码，不出现空白 / 报错）。具体兜底策略以 design/api 阶段确定。

### F2 修改配置（卡片 C 弹窗）下拉项替换为真实数据接口

- F2.1 卡片 C「调整配置」弹窗中的选择类字段，候选项由**前端静态枚举**替换为**真实数据接口**返回的可选项。
- F2.2 数据来源：**复用 CVM 申领页现有的选项接口 / hook**（如 `use-cvm-options`、`use-disk-options` 等），保证与 CVM 申领页选项口径一致。
- F2.3 覆盖的下拉字段以 C 弹窗现有可编辑字段为准（地域、可用区、机型、镜像 / 操作系统、磁盘类型等），具体字段与联动关系（如地域 → 可用区 → 机型级联）在 design/api 阶段对齐。
- F2.4 选项加载体验：下拉支持加载中 / 加载失败的合理反馈，沿用现网申领页交互。

---

## 4. 验收标准

- AC-1（F1）：卡片 A / B / D 中地域、可用区、机型、镜像、计费模式、需求类型、资源分配方式、磁盘类型均展示为可读名称，不再显示后端编码。
- AC-2（F1.4）：当某字段名称无法解析时，展示兜底内容（原编码或占位），不出现空白 / 报错 / `undefined`。
- AC-3（F2）：打开卡片 C 调整配置弹窗，各下拉项为真实接口数据，与 CVM 申领页一致；选择后可正常保存写回该行。
- AC-4（F2）：存在级联关系的下拉（若有）按真实数据正确联动，上层变更后下层候选刷新。
- AC-5：编辑保存后，卡片 B 回显的值与所选项一致，且展示为名称（呼应 F1）。

## 5. 待确认问题（design/api 阶段澄清）

1. **编码 → 名称的数据来源**：各字段名称从哪里取？是复用 CVM 申领页同一套选项数据（拿到 options 后按 value 反查 label），还是后端在 SSE 下行里补名称字段，或新增字典接口？（倾向复用 CVM 选项数据反查，待 api 阶段定）
2. **C 弹窗下拉字段与级联范围**：C 弹窗当前可编辑字段中哪些需要换成真实接口？是否需要地域→可用区→机型的级联？磁盘类型是否也走接口？
3. **名称展示形态**：是否需要「名称（编码）」并存，还是只展示名称？
4. **业务上下文**：复用 CVM 选项接口通常需要业务 id / 云账号等上下文，对话场景里这些上下文从哪来（会话中已采集 / 当前业务）？
