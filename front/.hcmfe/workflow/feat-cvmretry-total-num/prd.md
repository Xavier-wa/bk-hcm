# PRD: CVM 申请 - 修改需求重试 - 数量显示优化

## 1. 用户故事

**作为一个** CVM 资源申请提单人或审批人，  
**我想要** 在修改需求重试页面看到正确的当前需求数量，  
**以便于** 我能够基于实际的数量进行后续调整（如修改可用区、机型等），而不是被已过期的原始数量误导。

## 2. 业务背景

CVM 申请流程中，"修改需求"页面（需求重试）用于调整已提单但未生产的资源需求。在调整过程中，用户可以修改可用区、机型、数量等参数。

**问题现象**：当业务方在申请流程中修改了需求数量（例如从 3 台改为 2 台）后，再次进入"修改需求"页面调整其他参数（如可用区）时，页面显示的数量仍是原始提单数量（3 台），而非当前实际数量（2 台）。

这会导致：
- 用户误以为仍需生产原始数量，产生混淆
- 用户再次提交时可能覆盖已调整的正确数量

## 3. 功能需求

### 3.1 需求数量字段修正

- **当前行为**：修改需求页面使用 `origin_num`（提单时的原始数量）作为展示字段
- **期望行为**：修改需求页面应使用 `total_num`（当前总数量）作为展示和提交的字段

### 3.2 字段定义说明

| 字段 | 含义 | 适用场景 |
|------|------|----------|
| `origin_num` | 首次提单时的原始数量 | 仅用于历史追溯，展示原始单据信息 |
| `total_num` | 当前总数量（可能经过多次修改） | 用于需求展示、修改、提交 |

## 4. 验收标准

1. [ ] 进入 CVM 申请-修改需求页面时，数量显示为 `total_num`（当前总数量），而非 `origin_num`（原始数量）
2. [ ] 数量输入框初始值正确回填为 `total_num`
3. [ ] 提交修改时，提交的数量字段为当前实际数量（而非错误地使用原始数量）
4. [ ] 修改可用区/机型等操作时，数量字段不受影响，保持正确显示
5. [ ] 多次修改后（2 次及以上），每次进入修改页面均显示最新的 `total_num`

## 5. 边界场景

- **无数量变更场景**：如果用户从未修改过需求数量，`origin_num` === `total_num`，页面无变化
- **多次修改场景**：用户先 3→2，再 2→5，每次进入页面应显示正确的 `total_num`
- **修改后重新提交**：提交时使用修改后的数量，逻辑不受影响
- **新旧单据兼容**：历史单据中可能不存在 `total_num` 字段或字段为 null，应做好容错

## 6. 非功能性需求

- 仅涉及前端展示逻辑调整，不涉及后端接口改造
- 字段修正后应同步检查修改需求提交时的请求参数，确保前后一致
